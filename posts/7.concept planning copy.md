### Simulating the "group" environment

This assignment assumes a group setting, but I'm working alone. To still get the benefit of critique and divergence, I treated my tutor consultation as a stand-in for a group meeting. 


 I brought my initial rock climbing ideas (leaderboards, achievements, importing data from platforms like Strava) and asked directly: “What here actually solves a problem?” The answer: not much. The feedback reinforced that my concept was feature‑heavy but need‑light.

That conversation crystallised my main tension: I’m excited by ambitious interaction design, but my current technical skills, plus the unit constraints, force me to be strategic. I can’t just stack features and hope the technical side catches up later. I need a core flow that is both meaningful for users and buildable for me within the semester.

### Articulating the core problem


To get a sharper, I wrote a problem statement rather than a feature list:

Current community and forum platforms make it cumbersome to give precise, contextual feedback. Users often rely on long, text‑heavy comments and loose timestamps, which makes it hard to tie advice to specific moments or details. How might we create a more effortless feedback experience that feels closer to an in‑person conversation?


The flexibility of this helps if the climbing domain is technicall awkward and I can pivot to another community without changing the core functional requirements.

Drafting functional requirements (early version)
Instead of finalising requirements now, I treated this week as an initial pass that I expect to refine in Week 8 once I’ve explored feasibility more. The current breakdown looks like this:

Essential user‑facing functionality:

* Users can create a “feedback request” by uploading a primary artefact (e.g. video of a climb, photo of swatches, a DIY project image).

* Users can add structured metadata (location, level, date, relevant personal attributes such as height or skin tone, and specific issues they want feedback on).

* Other community members can leave comments that are anchored to specific parts of the artefact (e.g. a segment of the video or a region of the image).

* The requester can review feedback in a way that clearly links each comment to context, not just a flat comment list.

### Early alignment with technical decisions


Even though build sprints start in Week 8, I’ve already started testing the technical edges of my idea so I don’t design something impossible. I used AI tools (like code copilots) to sketch out how file uploads, basic data models, and timestamped comments might work in the tech stack used in this unit. The goal isn’t to write production code now, but to understand which parts are straightforward (e.g. storing comments in a database) and which are risky (e.g. precise video annotation or heavy file uploads).

From this early probing, I can see a trade‑off forming: a simpler “image with pinned comments” flow is more realistic than a fully featured video annotation system. 

If I decide to stay with climbing, that might mean encouraging users to upload short clips or still frames of problem areas instead of full, long videos. If I move to makeup shade feedback, image‑based annotation aligns even more naturally with my technical constraints.
